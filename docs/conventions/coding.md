# コーディング規約

## 適用範囲

React・Vite・TypeScriptによるアプリケーションと、Supabase上のTypeScriptによるサーバー処理を追加・変更するときに適用する。React固有の項目はフロントエンドに適用する。Pythonコードには[Pythonコードの記述規約](python-documentation.md)を適用する。

この規約は実装・レビューの基準である。アプリ本体とチェック環境は未整備のため、以下に記載するツールやCIが導入済みであることは意味しない。導入時には設定と実行方法をREADMEに記載する。

参照する公式資料は、各ルールの背景や言語・ツールの仕様を確認するための資料であり、資料全体を規約として採用するものではない。プロジェクトでのルールは本文に定め、書式の詳細は設定ファイルに委ねる。

## 書式と型

- TypeScriptの`strict`を有効にする。ESLintでコード上の問題、Prettierで書式を確認し、書式の詳細は設定ファイルを正とする。
- `any`は原則使わない。外部から受け取る不明な値は`unknown`として検証する。
- 型アサーションや非nullアサーションは、成立する根拠を明確にできる場合に限る。型エラーを隠すためには使わない。
- TypeScriptの型だけで実行時の入力を保証しない。利用者の入力や外部APIの応答は、必要な条件を境界で検証する。
- SupabaseのDB型はスキーマから生成し、DB変更時に更新する。生成ファイルは手編集せず、生成方法を文書化する。画面固有の型は必要に応じて別に定義する。

参照: [TypeScript strict](https://www.typescriptlang.org/tsconfig/strict.html)、[TypeScriptの型と型アサーション](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html)、[ESLintの基本概念](https://eslint.org/docs/latest/use/core-concepts/)、[PrettierとLintの役割](https://prettier.io/docs/comparison)。

## 命名とモジュール

| 対象 | 規則・例 |
| --- | --- |
| 変数・関数 | `camelCase`。意味の分からない略語を避ける |
| コンポーネント・型 | `PascalCase` |
| カスタムフック | `use`で始める |
| コンポーネントのファイル | 主な公開内容に合わせて`BookmarkList.tsx` |
| フックのファイル | `useBookmarks.ts` |
| その他のTypeScriptファイル | `bookmarkRepository.ts`など、主な公開内容に合わせる |
| DBのテーブル・カラム | `snake_case` |

命名表のうち、カスタムフックの`use`接頭辞はReactの規則に従う。それ以外の命名とファイル名は、表記を揃えて関連する定義を見つけやすくするためのプロジェクト方針である。

- 原則として名前付きexportを使う。参照側でも公開名を揃え、定義と利用箇所を追いやすくするためである。フレームワークなどが要求する形式は例外とする。
- 型だけの参照は`import type`を使う。循環参照は作らない。
- 関数やコンポーネントは役割を一つに絞り、表示・検証・通信など変更理由が異なる処理が混在したら分割する。最大行数による一律の制限は設けない。

## パスの表記

- ローカルモジュールのimportは相対パスを基本とする。深い相対パスが多くなり、参照先を追いにくくなった場合にパスエイリアスの導入を検討する。
- モジュール間の参照は[設計規約](design.md#責務と依存関係)の共通原則に従い、具体的な依存方向は別途整備するアーキテクチャドキュメントを参照する。
- ドキュメント内でファイルやディレクトリの場所を示す場合は、特記しない限りリポジトリルートからの相対パスを使う。Markdownの文書間リンクは、そのMarkdownファイルからの相対パスを使う。開発者の環境に依存する絶対パスは使わない。

## Reactと非同期処理

- コンポーネントのレンダー中に通信やデータ更新などの副作用を実行しない。Hooksはトップレベルで呼び出し、依存配列の警告を理由なく抑制しない。
- 状態から計算できる値を、別の状態やEffectで同期しない。
- イベントから開始する処理を含め、Promiseの失敗を扱う。Supabaseなどが戻り値で返すエラーも確認し、例外の捕捉だけで済ませない。
- リストの`key`には要素を識別できる安定した値を使う。
- ボタンや入力欄は用途に合うHTML要素を使い、入力ラベルとキーボード操作を確保する。
- 保存URLをリンクとして表示する場合は、許可するスキームを検証する。外部から取得したHTMLを無検証で描画しない。

参照: [ReactのHooksの規則](https://react.dev/reference/rules/rules-of-hooks)、[不要なEffectを避ける](https://react.dev/learn/you-might-not-need-an-effect)。

## コメントと依存関係

- コメントは日本語で判断理由や制約を説明し、コードから分かる動作の言い換えは避ける。
- 複雑な関数や、呼び出し方に制約のある関数には、目的・入出力・失敗条件など必要な説明を付ける。全関数への定型コメントは要求しない。
- 依存パッケージは既存機能で足りるか確認してから追加する。pnpm、lockfile、導入時の制限は[ADR 0005](../adr/0005-manage-javascript-dependencies-with-pnpm.md)に従う。
- ブラウザ用コードへNode.js専用APIやサーバー専用モジュールを持ち込まない。Supabaseのサーバー処理には、その実行環境で動作する依存関係を選ぶ。

## テストと変更時の確認

- 業務ロジックや入力検証は、通常の入力・境界値・不正な入力を確認する。
- UIは主要な操作と、読み込み中・失敗・データなしの表示を確認する。
- DBの認可は、本人・他人・未認証ユーザーによる操作を確認する。詳細は[設計規約](design.md)に従う。
- 不具合修正では原則として再発を検出するテストを追加する。困難な場合は代わりの確認方法をPRに記載する。
- テストは振る舞いや業務ルールを中心にし、実装内部を写しただけのテストは避ける。一律のカバレッジ数値は要求しない。
- TypeScriptの変更ではLint・書式・型チェック・関連テスト・ビルドを確認する。型チェックはViteのビルドとは別に実行する項目として用意する。未整備・未実施の項目は、理由とともにPRに記載する。
- Git・コミットの規約は[AGENTS.md](../../AGENTS.md)に従い、PRには変更理由、利用者への影響、検証結果を記載する。
