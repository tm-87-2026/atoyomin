# 設計規約

## 適用範囲と前提

アプリケーションの設計・実装・レビュー時に適用する。React・Vite・TypeScriptのSPAをCloudflare Pagesで配信し、認証・DB・必要なサーバー処理にSupabaseを使う構成を前提にする。

採用技術は既存のADRに従う。技術選定や大きな構成変更は`docs/adr/`に記録する。個々の関数分割など通常の実装判断にはADRを要求しない。

初版ではテーブルのRLSを対象に含める。Edge Functionsは導入を必須とせず、必要になった場合の認証・認可などの原則を定める。Storage固有のバケット構成やアクセス制御は初版では定めず、利用時に規約を補う。

## 責務と依存関係

この規約では、責務と依存関係に関する共通原則を定める。具体的な責務分割・依存方向・ディレクトリ配置は、別タスクで整備するアーキテクチャドキュメントを参照する。アーキテクチャドキュメントは現時点では未整備であり、この規約で特定の構成を固定しない。

- 各部分の責務を明確にし、変更理由が異なる処理が混在したら分離する。
- 依存関係を明確にし、循環依存を作らない。部分間で公開する窓口を絞り、内部の実装に依存する参照を広げない。
- 複数箇所で同じ責務が必要になった時点で共通化を検討する。見た目やコードの形が似ているだけでは共通化しない。
- クリーンアーキテクチャの厳密な適用、全クラスへのインターフェース、将来の拡張だけを理由にした抽象化は要求しない。アプリ未実装の段階で仮定に基づく構造を増やさず、必要な責務分離から始めるためである。
- 図は認証フローやサービス間連携など、文章やコードだけでは理解しづらい場合に作る。全機能へのクラス図・シーケンス図は要求しない。

## 状態管理とデータ取得

- 一時的なUI状態は、必要とする最小範囲で持つ。共有が必要になった場合に範囲を広げ、計算で求められる値を重複して保存しない。
- 画面の状態とサーバー上のデータを区別し、取得・更新処理の責務を明確にする。状態管理・データ取得のライブラリは初版では固定せず、必要性と導入理由を確認して選ぶ。共有状態やキャッシュの要求が具体化してから判断するためである。
- 読み込み中、取得失敗、データなしを区別する。更新後に再取得するか手元のデータを更新するかを決め、古い応答による上書きや二重送信を防ぐ。
- ログアウトやユーザー切り替え時は、前のユーザーのデータを状態やキャッシュに残して表示しないようにする。
- 一覧取得には並び順を定め、件数が増える処理では取得上限やページングを設ける。

## Supabaseとの境界

- 認証にはSupabase Authを使う。画面上の認証状態だけでアクセス権を保証しない。
- ブラウザからアクセスさせるテーブルはRLSを有効にし、必要な権限とポリシーだけを与える。ユーザー所有データは、参照・追加・更新・削除の各操作について所有者を制限する。更新時に所有者を変更して制限を逃れられないことも確認する。
- Supabaseへのアクセスには、DBスキーマから生成した型を適用したクライアントを使う。型の生成・更新は[コーディング規約](coding.md)に従う。
- 入力はUIで利用者にフィードバックし、整合性に必要な条件はDBの制約やサーバー側でも保証する。外部キー・一意性・必須項目などをアプリの条件分岐だけに任せない。
- 複数の更新を一体として成功させる必要がある場合は、DBのトランザクションなどで原子性を保証する。ブラウザからの連続リクエストだけに任せない。
- テーブル・制約・インデックス・RLS・権限の変更はマイグレーションで管理し、DB全体として適用順序を管理する。管理画面での手作業だけを履歴にせず、生成型と利用コードも整合させる。
- 秘密情報を要する外部API、特権操作、外部URLの内容取得など、ブラウザに任せられない処理はSupabase側で実装する。Edge Functionsなどの入口でも認証・認可を検証し、ブラウザから渡されたユーザーIDを信用しない。
- 本アプリのバックエンドから利用者が指定したURLにアクセスする際は、アクセス先とリダイレクト先を検証し、非公開サービスへのアクセスを防ぐ。また、過大な応答や長時間の待機で本アプリの処理に負荷がかからないよう、受信するデータ量と待機時間に上限を設ける。

## エラーと秘密情報

- 入力エラー、認証・権限エラー、通信障害などを区別し、失敗を握りつぶしたり成功扱いにしたりしない。画面には利用者が次に取れる行動を示す。
- 再試行を行う場合は回数を制限し、更新処理が重複しないことを確認する。
- 秘密情報・認証トークン・個人情報をコード、ログ、テストデータに記録しない。利用者向けメッセージには内部の詳細をそのまま表示しない。
- ブラウザにはSupabaseの公開用キーだけを渡す。公開用キーの秘匿を認可の代わりにせず、RLSで保護する。管理権限を持つキーやDB接続情報はサーバー側だけで扱う。
- `VITE_`付きの環境変数はブラウザへ公開される前提で扱う。秘密情報を含めず、環境変数の読み取りと必須値の検証の責務を明確にする。設定例には変数名とダミー値だけを記載する。

## Cloudflare Pagesと環境の分離

- Cloudflare Pagesはフロントエンドの静的配信に使い、初期構成にWorkers・Pages Functionsは追加しない。サーバー処理はSupabaseで実装する既存ADRに従う。
- mainを本番、PRをプレビューとして扱う。Viteのビルド時に接続先などの設定を取り込むため、本番とプレビューそれぞれのビルド環境変数を設定し、変更時は再ビルドする。
- プレビューの作成だけではSupabaseのDBは分離されない。ローカル・プレビューは本番と別のSupabase環境に接続させ、本番データや本番用の秘密情報を使わない。非本番環境を共有する場合はデータの競合とマイグレーションの影響を確認する。
- Supabase Authのリダイレクト先は、ローカル・プレビュー・本番で必要なURLを明示的に許可し、不要な範囲へ広げない。
- デプロイ時は、画面内の遷移に加えて、子パスへの直接アクセス・再読み込み・認証後の復帰を確認する。
- DB変更は配信済みのフロントエンドとの互換性を確認して適用する。破壊的変更では移行順序と復旧方法を決め、フロントエンドのロールバックだけでDBも戻るとは扱わない。

## 設計変更の検証

- RLSと権限の変更は、本人・他人・未認証ユーザーで対象の各操作を確認する。管理権限を持つクライアントだけで成功を確認して済ませない。
- マイグレーションは非本番環境で適用し、想定するスキーマ・制約・権限を再現できることを確認する。
- 認証、保存、一覧、読了変更など、変更に関係する主要な利用経路を確認する。テストとPRの記録は[コーディング規約](coding.md)に従う。
