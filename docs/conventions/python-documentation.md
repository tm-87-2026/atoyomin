# Pythonコードの記述規約

## 適用範囲

この規約は、リポジトリ内のPythonコードを追加または変更するときに適用します。

## 方針

コードを初めて読む人が、次の順で理解できる状態を目指します。

1. このファイル・クラス・関数は何のためにあるか。
2. 呼び出すには何が必要で、何が返り、どのような失敗があるか。
3. 関数内で、どの段階で何をしているか。

コメントとdocstringは日本語で書きます。docstringの書式は、Google Python Style Guideを基準にします。

## 記述する場所と内容

| 場所 | 記述するもの | 読み手に伝えること |
| --- | --- | --- |
| モジュール先頭 | docstring | ファイルの役割と、扱う処理の全体像 |
| クラス先頭 | docstring | クラスが表すものと責務 |
| 関数先頭 | docstring | 関数の目的と、呼び出し側が知るべき入出力・例外 |
| 関数内 | ブロックコメント | 処理の段階、または実装上の判断理由 |

## 関数のdocstring

すべての関数に、目的を表す要約文を置きます。呼び出し側が知る必要がある情報は、次の見出しで記述します。

| 見出し | 記述する場合 |
| --- | --- |
| `Args:` | `self`以外の引数を受け取る場合 |
| `Returns:` | 値を返す場合 |
| `Yields:` | ジェネレータの場合 |
| `Raises:` | 呼び出し側が扱うべき例外を送出する場合 |

型注釈がある場合、型をdocstringに重複して書きません。引数・戻り値・例外がなく、1文で役割を十分に表せるテストメソッドなどは、1行docstringを使います。

関数のdocstringの直後には、必ず空行を1行置きます。これはこのリポジトリ固有の読みやすさの規約です。

## 関数内のコメント

ブロックコメントは、docstringでは表せない処理の流れや判断理由を説明するために使います。

- 完全な文として書きます。
- 説明対象のコードの直前に置きます。
- 新しい処理段階を説明するコメントの前には、空行を1行置きます。
- コメントと説明対象のコードの間には、空行を置きません。
- 行末コメントは原則使いません。
