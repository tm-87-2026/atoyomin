# Supabaseで利用する機能と用途を整理し文書化する設計

## 基本情報

- 対象Issue: #55
- 状態: 合意済み
- 合意日・合意対象: 2026-11-10（Asia/Tokyo）、設計書およびTODO全体
- 正とする要求書: [要求書](requirements.md)（2026-11-10、合意済み）

## 設計の概要

人間が最低限読む範囲は基本情報とこの節とする。後続サブエージェントと詳細を知りたい人間は、[詳細設計](#詳細設計)も読む。

### 全体構成

`docs/development/supabase-features.md`を、Supabaseの利用状態と用途を参照する恒久資料として新設する。資料は機能一覧を中心に、分類の意味、各行の根拠、関連タスクとの境界を記載する。実装・既存方針・今回以後に判断する事項を同じ表の状態と根拠で区別することで、利用候補を採用済みと誤認しないようにする。

### 主要な設計判断と採用理由

- 恒久資料は`docs/development/`に置く。開発時のセットアップ・運用資料である[SupabaseとCloudflare Pagesのセットアップ](../development/supabase-cloudflare-pages.md)と近接させ、要求書の配置条件を満たす。詳細は[成果物・変更範囲](#成果物変更範囲)を参照する。
- 要求書で定めた利用状態の記録区分は「実装済み」「既存の方針で利用を予定」「現時点で利用しない」「今後の検討対象」の4区分とする。この区分は将来の機能にも使う記録規則であり、今回の5機能が4区分すべてに分かれることを意味しない。今回の分類は、Database・RLSを実装済み、AuthとEdge Functionsを既存の方針で利用を予定、StorageとRealtimeを現時点で利用しないとする。詳細は[利用状態と根拠の記載](#利用状態と根拠の記載)を参照する。
- 機能別の詳細設計は担当Issueへリンクする。#55では機能の採否・用途の現在地だけを扱い、#20の認証・RLS詳細、#47の環境設定・実動作、#49の責務分割を重複して定義しない。詳細は[関連タスクとの境界](#関連タスクとの境界)を参照する。

### 適用条件と運用上の制約

- 資料は現時点のリポジトリ内の実装とAccepted ADRを根拠にする。外部サービスの料金・提供条件を新たに断定しない。
- `VITE_`付きの公開用キーでブラウザからData APIへ接続する場合、RLSが認可の前提である。資料はこの共通方針を示すが、ユーザー固有の認可ポリシーを設計しない。
- 「現時点で利用しない」機能は、当該機能を必要とする要求が生じた時点で、担当タスクで採否と個別設計を再検討する。

### 成立を確認した根拠と限界

`src/lib/supabase.ts`は公開用キーを用いる型付きSupabaseクライアントを作成し、`20261107000000_create_app_status.sql`は`public.app_status`でRLSを有効化して`anon`および`authenticated`への`SELECT`だけを許可している。このため、Database・RLSの最小構成は実装済みと確認できる。[ADR 0002](../adr/0002-use-supabase-for-backend-services.md)、[ADR 0003](../adr/0003-use-cloudflare-pages-for-frontend-hosting.md)、[設計規約](../conventions/design.md)はAuth、必要時のSupabase側サーバー処理、RLS、Cloudflare Pagesとの境界に関する既存方針の根拠となる。

この工程では実環境への接続、認証、Storage、Realtime、Edge Functionsの動作は検証しない。#47の環境構築・実動作確認、#20の認証詳細、将来の個別導入タスクで確認する。

### 人間の判断に関わる未決事項

なし。

## 詳細設計

### 成果物・変更範囲

最終的に追加する資料は`docs/development/supabase-features.md`とする。想定読者は、Supabase機能の利用可否を確認して機能開発を計画・実装する開発者である。

資料は次の順序で構成する。

1. 資料の目的と対象範囲を示し、列挙が全機能の採用を意味しないことを明記する。
2. 利用状態を記録する4区分と、今回の5機能への分類結果を分けて示し、実装事実・既存方針・未決事項を根拠欄で区別する規則を示す。
3. Auth、Database・RLS、Edge Functions、Storage、Realtimeを一覧化し、用途、利用状態、根拠、再検討条件または担当タスクを記載する。
4. #20、#47、#49との責務境界と、ADR・規約・実装へのリンクを記載する。

資料はアプリケーションコード、マイグレーション、既存ADR、既存セットアップ手順を変更しない。Authの方式・RLSポリシー詳細、CloudflareやSupabaseの設定手順、モジュール配置は対象外とする。

### 利用状態と根拠の記載

利用状態の4区分は資料全体で用いる記録規則である。今回の5機能には「今後の検討対象」を割り当てず、次の分類と記載内容を用いる。

| 機能           | 利用状態               | 本アプリでの用途                                    | 根拠と扱い                                                                                                                               |
| -------------- | ---------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Auth           | 既存の方針で利用を予定 | 利用者の認証                                        | [設計規約](../conventions/design.md)とADR 0002の方針。方式、フロー、トークン、ユーザーごとのRLSは#20で決定する。                         |
| Database・RLS  | 実装済み               | 接続確認用の`public.app_status`を読み取る           | `src/lib/supabase.ts`および接続確認用マイグレーション。公開用キーによるブラウザアクセスでRLSを有効化し、`SELECT`だけを許可している。     |
| Edge Functions | 既存の方針で利用を予定 | 秘密情報を要する外部API、特権操作などのサーバー処理 | [設計規約](../conventions/design.md)とADR 0003の方針。必要なサーバー処理の要求が生じた担当タスクで、個別処理の採否と実装詳細を検討する。 |
| Storage        | 現時点で利用しない     | なし                                                | 現行実装・既存方針にファイル保存の要求はない。ファイル保存の要求が生じた担当タスクで、バケット構成とアクセス制御を含めて再検討する。     |
| Realtime       | 現時点で利用しない     | なし                                                | 現行実装・既存方針にリアルタイム更新の要求はない。リアルタイム更新の要求が生じた担当タスクで、用途と利用方式を再検討する。               |

この表は、最終資料で示す今回の機能分類と根拠の対応を表す。パスは最終資料からの相対パスに置き換え、IssueはGitHub上の対象Issueへリンクする。実装事実はコードまたはマイグレーション、既存方針はAccepted ADRまたは規約、現時点で利用しない機能は再検討条件で根拠を示す。「今後の検討対象」を将来記録する場合は、利用の要否を判断する担当タスクまたは条件を根拠として併記する。

### 検証方針

文書変更として、実装前に次の代表シナリオを確認基準にする。

| 対象要求         | 代表シナリオ                                          | 判定基準                                                                                                                                                | 検証方法                                                          |
| ---------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| REQ-001、REQ-004 | 開発者が最終資料の一覧から5機能の用途と状態を確認する | Database・RLSが実装済み、AuthとEdge Functionsが既存の方針で利用を予定、StorageとRealtimeが現時点で利用しないと分類され、資料が`docs/development/`にある | 資料の見出し・一覧・パスを目視照合する                            |
| REQ-002          | 開発者が実装済みの利用と将来方針を取り違えない        | Database・RLSだけを実装済みとし、公開用キー、Data API、`app_status`、RLS読み取り専用の根拠が実装と一致する                                              | `src/lib/supabase.ts`とマイグレーションを資料の記述と目視照合する |
| REQ-003          | 開発者が既存方針と各タスクの役割を追える              | ADR 0002、ADR 0003、設計規約、#20、#47、#49へ参照でき、対象外の詳細設計を追加していない                                                                 | リンク先と資料の境界記述を目視照合する                            |
| REQ-004          | 未採用機能の将来判断を追える                          | StorageとRealtimeに要求発生時の再検討条件があり、Edge Functionsには個別処理の採否・実装詳細を検討する担当タスクの境界がある                             | 機能一覧の根拠・再検討欄を目視照合する                            |

### 未決事項

なし。要求変更または設計変更が必要になった場合は、[開発ワークフロー](../development/development-workflow.md)の戻り方に従い、親エージェントを通じて要求または本設計を再確認する。
