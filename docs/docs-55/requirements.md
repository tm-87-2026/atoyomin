# Supabaseで利用する機能と用途を整理し文書化する要求

## 基本情報

- 対象Issue: #55
- 状態: 合意済み
- 合意日・合意対象: 2026-11-10（Asia/Tokyo）。資料の恒久配置先を`docs/development/`とすること、利用状態の分類、未採用機能は該当する要求が生じた時点で再検討すること、および要求書全体。

## 背景・目的

Supabaseをバックエンドサービスとして採用しているが、現時点で実装済みの機能と、今後の機能開発で利用を検討する機能が一か所で区別されていない。開発者が必要な機能とその用途、未採用・未決定の機能を既存の決定と矛盾なく参照できる資料を用意する。

## 対象範囲

### 対象

- Supabaseの機能を、実装済み、既存の方針で利用を予定するもの、現時点で利用しないもの、今後の検討対象に区分し、それぞれの本アプリにおける用途を整理すること。
- 整理資料を`docs/development/`に配置すること。
- 少なくともAuth、Database・RLS、Edge Functions、Storage、Realtimeを対象に、各機能を利用するか否かと、その状態を明記すること。
- 資料内で、既存の実装事実、既存ADR・規約で決定済みの方針、今回以後に判断が必要な事項を区別し、根拠資料を参照可能にすること。
- #20、#47、#49が扱う認証詳細、環境構築・動作確認、アーキテクチャの責務分割と重複しないよう、各タスクとの境界を示すこと。

### 対象外

- 認証方式、認証リクエストフロー、トークンの管理方法、ユーザーごとのRLSポリシーの詳細設計（#20）。
- Cloudflare PagesまたはSupabaseのプロジェクト設定、デプロイ、環境構築、実環境での動作確認（#47）。
- アプリケーションの責務分割、依存関係、モジュール構成、フォルダー配置の決定（#49）。
- Storageのバケット構成・アクセス制御、Realtimeの利用方式、Edge Functionsの個別処理の設計・実装。
- Supabaseの各機能を新たに採用する決定、ADRの作成・更新、アプリケーションコードまたはマイグレーションの変更。

## 要求

### REQ-001: Supabase機能と用途を参照できる資料

- 開発者が、Supabaseで扱う機能ごとに、本アプリでの用途と利用状態を参照できる資料を利用できること。
- 資料はAuth、Database・RLS、Edge Functions、Storage、Realtimeを漏れなく扱い、列挙した機能をすべて採用することを意味しないこと。
- 資料は既存のADR、規約、実装、関連Issueを参照し、根拠のない利用方針を確定事項として記載しないこと。

### REQ-002: 実装済みの事実と将来の方針の区別

- 現在実装済みのSupabase利用を、将来の利用方針および未決事項と区別して記載すること。
- 現時点の実装済みの利用には、ブラウザから公開用キーでSupabase Data APIへ接続し、`public.app_status`をRLS有効・読み取り専用で参照する最小構成を含めること。
- 将来の方針または検討事項は、決定済みの方針か未決定かを明記し、未決定のものを採用済みとして扱わないこと。

### REQ-003: 既存方針との整合

- 資料は、Supabaseをバックエンドサービスとして採用し、PostgreSQL、認証、必要に応じたサーバー処理を利用候補とする既存方針と整合すること。
- ブラウザからデータへ直接アクセスする際にRLSが必要である既存方針を明示し、具体的な認可設計を本タスクの成果物に含めないこと。
- 資料は、Cloudflare Pagesの初期構成にWorkers・Pages Functionsを追加せず、サーバー処理が必要な場合にまずSupabaseの機能を検討する既存方針と矛盾しないこと。

### REQ-004: 資料の配置と利用状態の記録

- 資料を`docs/development/`に配置すること。
- 各機能の利用状態を、実装済み、既存の方針で利用を予定するもの、現時点で利用しないもの、今後の検討対象のいずれかに分類して記載すること。
- 「現時点で利用しない」とした機能は、その機能を必要とする要求が生じた時点で再検討することを記載すること。
- 今後の検討対象とした機能は、利用の要否を判断する担当タスクまたは条件を記載すること。

## 完了条件

- REQ-001からREQ-004を満たす資料が参照可能である。
- 資料がSupabaseの主要機能ごとに用途と利用状態を示し、実装済み・既存方針・未決事項を区別している。
- 資料と既存ADR、設計規約、#20、#47、#49の役割分担に矛盾がないことを確認できる。
- 資料の配置先、利用状態の分類、未採用機能の再検討条件、および要求書全体へのユーザーの明示的な合意が記録されている。

## 未決事項

なし。
