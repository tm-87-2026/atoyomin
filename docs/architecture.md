## 目的と位置付け

あとよみんの実装・レビューで参照する初期設計方針をまとめる。現時点ではアプリケーション本体は未実装であり、本書は実装済みの構成を説明するものではない。

開発は3人で業務時間外に行い、2027年3月19日までにプロダクトバックログのStoryをすべて実装することを目指す。Supabaseは全員未経験であり、React・TypeScriptの経験にも差がある。コードの役割と変更の影響をチームで理解し、一定の品質で開発できることを重視する。

初めから特定のアーキテクチャに固定せず、共通の設計原則と本書に沿って実装を始め、実際のコードをもとに構成を見直す。判断の背景は[ADR 0011](adr/0011-evolve-architecture-through-implementation.md)に記録する。

## 全体構成と責務

採用技術は[ADR 0002](adr/0002-use-supabase-for-backend-services.md)、[ADR 0003](adr/0003-use-cloudflare-pages-for-frontend-hosting.md)、[ADR 0004](adr/0004-use-react-vite-and-typescript-for-the-web-frontend.md)に従う。

| 構成要素 | 役割 |
| --- | --- |
| React・Vite・TypeScript | ブラウザーで動くSPAとして、画面表示とユーザー操作を扱う |
| Cloudflare Pages | フロントエンドのビルド成果物を配信する |
| Supabase Auth | ユーザー認証を担う |
| SupabaseのPostgreSQL・データAPI | データの保存・取得とアクセス制御を担う |
| Supabase上のサーバー処理 | LINEやLLMなど外部サービスとの連携を扱う。具体的な実装構成は未決定 |

Cloudflare Workers・Pages Functionsは初期構成に含めない。サーバー処理はSupabaseで実装する。

フロントエンドとバックエンドはAPIを通じて連携する。ブラウザーからデータAPIを直接利用する場合は、DB側のRLS（行ごとのアクセス制御）で利用者のデータを保護する。画面で表示を制限するだけではアクセス制御にならない。

LINEからの保存、記事の一覧・検索・詳細、要約、通知、アクティビティ分析を設計の対象とする。各処理のAPI、データ構造、LINE利用者とアプリ利用者の対応付けは、それぞれの機能設計で具体化する。

## フロントエンドの初期方針

React公式の[Thinking in React](https://react.dev/learn/thinking-in-react)に沿って開発する。ReactでUIを組み立てるための設計手順として参照する。

1. ワイヤーフレームや画面案から、役割ごとにコンポーネントを分割する。
2. データを渡して表示する静的な画面を作る。
3. 変化を記憶するために必要な最小限のstateを特定する。
4. 各stateを利用するコンポーネントを確認し、stateを持つ場所を決める。
5. ユーザー操作からstateを更新し、表示へ反映する流れをつなぐ。

### state・propsとデータの流れ

stateは、コンポーネントが再描画をまたいで記憶し、更新を表示に反映する値である。propsは、親から子へ渡すデータや関数である。親のstateを子へ渡すと、その子にとってはpropsになる。

既存のstateやpropsから計算できる値は、原則として別のstateに保存しない。例えば記事データと検索条件から絞り込み結果を計算できる場合、その結果を重複して保持しない。

stateを使うコンポーネントの共通の親など、適切な場所にstateを置く。データは親から子へpropsで渡す。子での操作が親のstateを変える場合は、親が渡した更新用の関数を子から呼ぶ。

APIから取得した結果は、コンポーネントのstateやデータ取得ライブラリで管理し、必要な子へpropsで渡す。取得中・失敗時の状態も表示に反映する。データ取得ライブラリの採否は未決定である。

### 責務の分離

上記の手順で実装し、表示・状態・操作の処理を追いにくくなった場合に、コンポーネントやカスタムHookへの分離を検討する。

カスタムHookはReactの状態を伴うロジックを分離・再利用する手段として扱う。通常の計算や判定まで一律にHookにしない。分離時は[React公式のカスタムHooksの指針](https://react.dev/learn/reusing-logic-with-custom-hooks)を参照する。

### コードの配置と依存関係

フロントエンドの配置は[Bulletproof ReactのProject Structure](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)を参考に、次の原則に従う。Thinking in Reactは画面の組み立て方、Bulletproof Reactは関連コードのまとめ方と依存関係の参考資料として使う。採用理由は[ADR 0012](adr/0012-organize-frontend-by-feature.md)に記録する。

#### 関連するコードを機能の近くに置く

記事管理や認証など、同じ目的で変更するコードを `src/features/<機能名>/` にまとめる。一覧・検索・詳細のように同じ記事データを扱う画面は、まず同じ機能として考える。画面やStoryごとに機械的に機能を分けない。

機能内では、表示を `components/`、API呼び出しを `api/`、抽出したカスタムHookを `hooks/` に置く。型や通常の関数も、その機能だけで使う間は機能内に置く。必要になったディレクトリーだけ作成する。

#### 共通部分には機能固有の知識を持ち込まない

特定の機能に依存せず複数の機能で使う部品は、`src/components/`、`src/hooks/`、`src/lib/` などに置く。例えば汎用ボタンは共通部品、記事の読了操作を持つボタンは記事管理の部品とする。Supabaseクライアントの初期設定は `src/lib/`、記事テーブルへの問い合わせは記事管理の `api/` に置く。

配置例は次のとおり。これは初期実装時の例であり、必要なものから作成する。

```text
src/
  app/                    ルーティング、画面の組み立て、全体の初期設定
  features/
    articles/
      components/         記事一覧・検索・詳細などのUI
      api/                記事データの取得・更新
      hooks/              記事管理で使うカスタムHook
    auth/                 認証に関するコード
  components/             機能に依存しない共通UI
  hooks/                  機能に依存しない共通Hook
  lib/                    Supabaseなどのクライアント初期設定
```

#### importの方向を揃える

ここでいう依存は、実行時の通信やデータの流れではなく、コードのimport関係を指す。

| importする側 | importできる先 |
| --- | --- |
| `app/` | 機能、共通部分 |
| 各機能 | 同じ機能の内部、共通部分 |
| 共通部分 | 共通部分 |

別の機能を直接importしない。複数の機能を使う画面は `app/` で組み合わせ、必要な値や操作をpropsで渡す。共通部分から機能や `app/` をimportしない。

例えば認証と記事管理を組み合わせる場合は、`app/` が両方を利用する。記事管理が認証画面の内部コードを参照する形にはしない。共通化に迷った場合は、コードを移す前に、そのコードが機能固有のデータやルールを必要とするかを確認する。

設計・レビューでは、変更する機能のコードがまとまっているか、共通部分に機能固有の処理が入っていないか、上記のimport方向を守っているかを確認する。

## バックエンドの初期方針

Supabaseが提供する認証・データAPIと、自分たちで定義するテーブル・制約・RLS、自分たちで書くサーバー処理を区別する。バックエンドの責務は、サーバー処理のコードだけで完結するものとして扱わない。

共通の設計原則に従って実装し、Supabaseの処理の流れと制約を確認してから、業務処理・DBアクセス・外部サービス連携をどこまで分離するか判断する。

最初の確認には[Issue #47](https://github.com/tm-87-2026/atoyomin/issues/47)のミニマルな実装を利用する。認証方式・認証リクエストの流れ・トークン管理の詳細は[Issue #20](https://github.com/tm-87-2026/atoyomin/issues/20)で扱う。

## 未決定事項と見直し

次の事項は、実装を通じて具体化する。

- 画面の状態と操作を担う処理の分離方法、通信処理の分離方法、状態管理・データ取得ライブラリ。
- バックエンドの層構成、インターフェースによる依存の分離、DBとサーバー処理への業務ルールの配置。
- バックエンドの具体的なフォルダー構成とAPI境界。

最初の動く機能ができた段階で、処理を追えるか、変更箇所を判断できるか、レビューで責務を説明できるかをチームで確認する。理解・変更しにくい箇所があれば、具体的なコードをもとにリファクタリングと配置ルールを検討し、本書を更新する。重要な判断はADRに残す。

共通の設計原則は設計規約、本アプリ固有の構成・適用方針は本書、選択の背景と理由はADRで管理する。このブランチには設計規約が未反映のため、[PR #48](https://github.com/tm-87-2026/atoyomin/pull/48)の取り込み時に参照と整合性を確認する。
