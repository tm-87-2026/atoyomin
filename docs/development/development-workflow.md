# Codexと進める開発ワークフロー

## 目的と適用範囲

要求の認識ずれを実装へ持ち込まず、前の会話履歴がなくても作業を再開できるよう、worktreeを開いた後の工程・成果物・移行条件をここに定める。本書を運用ルールの正本とし、起動操作は[development-workflow Skill](../../.agents/skills/development-workflow/SKILL.md)を使う。ブランチ・worktreeの準備は[task-start](../../.agents/skills/task-start/SKILL.md)が担当する。

すべてのタスクで、まず目的・範囲・完了の目安をユーザーとすり合わせる。非実装タスクは、その後に必要な作業と確認を行い、根拠を既存文書または報告へ残す。4工程・4ファイルを一律に求めず、非実装専用のフローも設けない。小規模変更で工程をまとめる場合は、対象工程・省く区切り・理由・確認方法をユーザーと合意して記録する。Codexだけの判断で省略しない。

## 役割とコンテキスト

ユーザーと対話を続けるCodexを「親エージェント」、工程の作業を担う別のエージェントを「サブエージェント」と呼ぶ。親エージェントは相談・合意・進行管理を担う。工程ごとに会話履歴を渡さない新規サブエージェントへ交代し、同時に動かすサブエージェントは1つとする。設計とTODOは同じサブエージェント、テスト作成と実装も同じサブエージェントが扱う。

サブエージェントは指定された成果物と規約を自分で読み、親エージェント・前のサブエージェントの会話や要約だけを根拠にしない。質問は親エージェントへ返し、親エージェントがユーザーの回答を仲介する。回答はサブエージェントが成果物へ反映し、明示的な合意は親エージェントが確認・記録する。サブエージェントの完了報告からユーザー合意を推定しない。

サブエージェント機能や履歴分離が使えない場合は、その状況を伝え、新規会話に同じ開始情報を渡す方法を相談する。同じ会話での継続を分離済みと扱わない。方式の背景は[ADR 0011](../adr/0011-separate-development-context-by-phase.md)と[ADR 0012](../adr/0012-coordinate-phase-agents-through-artifacts.md)を参照する。

## 工程と成果物

各工程の入力・出力と移行条件を次の表に示す。すべてのサブエージェントは、表の入力に加え、AGENTS.md、適用規約・Skill、テンプレート、関連ADR、必要な既存コード・設定・現状資料を読む。入力を直前の工程の成果物だけに限定しない。

| 工程 | Input | Outputの必須内容 | 完了・移行条件 |
| --- | --- | --- | --- |
| ありたい姿のすり合わせ | Issue、ユーザー要望、現状資料 | `requirements.md`：目的、要求ID付き要求、対象・対象外、完了条件、未決事項、合意状態 | 手段の選定は行わず、要求の充足判断を妨げる未決事項を解消する。ユーザーの明示的な合意を記録して設計を行うサブエージェントへ渡す |
| 設計・TODO洗い出し | 合意済み要求書、既存コード・設定・現状資料 | `design.md`：要求に対応する設計・判断理由・検証方針・未決事項。`todo.md`：要求ID付き作業・完了条件・検証方法・依存関係。両方に合意状態 | 全要求への参照と検証方法・依存順序を明確にし、実装・検証を妨げる未決事項を解消する。設計・TODO全体へのユーザーの明示的な合意後に実装を行うサブエージェントへ渡す |
| 実装・単体テスト | 合意済み要求書・設計書・TODO、既存コード・設定 | 変更一式、TODOの進捗・実施内容・検証結果と根拠・残る課題 | 実装・検証対象のTODOが完了し、必要なチェックが成功している。親エージェントが結果を受け、ユーザー確認を待たず完了確認を行う新規サブエージェントを起動できる |
| 完了確認 | 合意済み要求書・設計書、更新したTODO、実際の差分・検証結果 | `verification.md`：全要求の判定と根拠、TODOと対応要求の照合、差分・検証結果、残る課題、通過可否 | 全要求と実装・検証対象の全TODOに不足がないことを確認する。親エージェントが結果を報告し、コミット前の確認を待つ |

未決事項を残す場合は、実装・検証を妨げない理由、当面の方針、決める時期・条件を設計書に記録し、ユーザーと合意する。判断を妨げる未決は残して進まない。

完了確認自身と、通過後のコミット・PR確認は実装から移行する際の完了対象から除く。完了確認自身は確認工程で完了させ、通過後の手続きが未実施であることを理由に検証を失敗としない。

## 成果物の配置と記録

成果物は `docs/<prefix>-<Issue番号>/` に置き、prefixは[task-startの対応表](../../.agents/skills/task-start/SKILL.md#ブランチのprefix)と作業ブランチに揃える。各ファイルは必要な工程で作り、[要求書](../templates/requirements.md)・[設計書](../templates/design.md)・[TODO](../templates/todo.md)・[完了確認書](../templates/verification.md)のテンプレートを使う。

正式な成果物はMarkdownを基本とし、構造や流れには必要に応じてMermaidを使う。HTMLは画面の動作・操作感を確認する補助資料にできるが、決まった仕様はMarkdownへ反映する。

- 各成果物の基本情報に、状態（案／合意済み／再確認待ち）、合意日・合意対象を残す。提案と決定を区別し、会話を丸ごと転記しない。
- 要求IDはIssue内で `REQ-001` 形式の連番とし、独立して充足判断できる要求に付ける。既存IDは振り直さず、削除番号も再利用しない。設計・各TODO・完了確認から参照する。専用の対応表は必須にしない。
- 要求書のレベル2見出しの名称・順序を維持し、要求はレベル3見出しのID・要求名と、その下の同じ階層の箇条書きで書く。小見出し、説明の図表は必要に応じて追加する。
- 各成果物は次のサブエージェントが判断できる最小限とし、行数や項目数のノルマを設けない。既出内容は参照する。詳細設計が不要ならその旨、未決がなければ「なし」と書く。
- 設計書は概要と詳細の2層に分ける。人間の最低限の読了範囲は基本情報・概要、後続サブエージェントは詳細も読む。概要に構成・選定理由・代償・成立条件・検証の根拠と限界を示し、詳細へリンクする。
- 重要な仕様・設計判断は[adr-writing](../../.agents/skills/adr-writing/SKILL.md)に従って `docs/adr/` へ記録し、関連成果物から参照する。新規ADRはProposedとし、明示承認がある場合だけAcceptedへ変える。

## 実装と検証の進め方

コード変更はTDD（テスト駆動開発）で進める。1つの振る舞い、関連する正常系・異常系などをまとまりとして、意図した失敗の確認、実装、成功確認、必要な整理を反復する。テスト1件ずつには固定せず、失敗原因と実装目的を追える範囲をサブエージェントが判断する。

文書・Skillだけの変更は、形式的なコードの単体テストを追加せず、先に不成立を識別できる代表シナリオ・確認基準を定め、変更後に照合する。TODOの実施記録には対象IDと「何を検証し、どうだったか」を短く残す。複数TODOで同じ根拠を共有でき、詳細ログは参照で示す。

完了確認を行うサブエージェントは要求・設計・TODOと実際の変更・根拠を照合し、必要なチェックを行う。別のサブエージェントによる確認でも誤りの発見は保証されない。今回の導入検証は[代表シナリオ](../testing/development-workflow.md)で扱い、実行済み結果と計画を区別する。結合テストの具体的な運用は今回の定義に含めない。

## 引き継ぎと変更時の戻り方

引き継ぎ前に親エージェントは、有効な合意、必要な判断理由、未決事項を成果物へ反映する。開始情報はSkillの例に沿って渡し、専用の引き継ぎファイルを必須にしない。同じ工程のレビュー修正は同じサブエージェントが行えるが、次工程にサブエージェントを再利用しない。親エージェントが交代・再開する場合も成果物の合意記録から進行を判断する。

問題の種類と再開条件を次の表に示す。

| 発見事項 | 戻る先と再開条件 |
| --- | --- |
| 入力の不足・矛盾、合意範囲が不明 | 依存作業を止め、ファイル・要求ID・疑問を親エージェントへ返す。親エージェントが前の合意を確認し、不明ならユーザーへ相談する |
| 要求変更が必要 | 親エージェントが変更案と影響を示す。要求を整理する新規サブエージェントが案を作り、要求への明示合意後、設計を行う新規サブエージェントが設計・TODOを見直す。更新後の設計・TODOへの明示合意後、実装を行う新規サブエージェントが再開する |
| 要求を変えず設計変更が必要 | 設計を行う新規サブエージェントが案とTODOへの影響を示し、親エージェントが相談する。設計・TODOへの明示合意後、実装を行う新規サブエージェントが再開する |
| 実装中の想定した失敗、設計内で直せる不備 | 同じサブエージェントがTDD・修正を続ける。要求・設計の変更が必要と判明すれば上記へ戻る |
| 完了確認で設計内の実装不備 | 対応TODOを未完了へ戻し根拠を残す。実装を行う新規サブエージェントが修正し、完了確認を行う新規サブエージェントが再確認する |
| 工程をまとめたい | 目的と適用範囲に記載した合意を得て記録するまで、通常の区切りを維持する |

変更合意前は元の合意済み本文を書き換えず、案と影響を区別する。承認後は現行本文・基本情報・未決事項を新しい合意に揃え、旧案・旧状態と区別する。影響する後続成果物を再確認待ちにし、完了TODO・検証根拠の有効性を見直す。影響項目は再検証し、影響しない結果は理由を添えて引き継ぐ。影響不明なら再検証する。要求IDは維持し、判断変更に関わるAccepted ADRは直接変えず新規ADRで扱う。

## 完了報告と公開の境界

確認通過後は、変更内容・検証結果・残る課題を親エージェントが報告し、コミット前にユーザーの確認を得る。通過だけでコミット・push・PR作成へ進まない。了承された変更を論理単位でコミットしたら、AGENTS.mdに従い作業ブランチへpushする。

コミット了承はPR作成の了承を含まない。PR作成前に別途ユーザー確認を得る。PRの文面作成・レビューは[pr-writing](../../.agents/skills/pr-writing/SKILL.md)に従い、文面確認の指定があればその承認も守る。

Issue起票・ラベル・Project登録は[task-create](../../.agents/skills/task-create/SKILL.md)の責務であり、要求書完成を起票条件にしない。着手準備、ADR承認、PR文面の責務を本ワークフローで置き換えない。
