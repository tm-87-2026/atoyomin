# ADR 0008: WSLのSSH agent設定をコンテナ接続前の初回セットアップで準備する

## Status

Accepted — 2026-11-02。ADR 0007を補足する。

## Context

WSL上の開発コンテナから、ホストのSSH agent（秘密鍵による認証要求を受ける常駐プログラム）を標準転送で利用したい。agentが動いていても、Dev Containersが接続先を取得できなければ転送できない。

#28では、手動でagentを起動したWSLターミナルからは接続できたが、コンテナ起動ログにはホストの`SSH_AUTH_SOCK`（agentの通信窓口のパス）が未設定と記録された。WSLの`~/.profile`に一時的に接続先を設定し、VS Codeを開き直すと標準転送とGitHub接続が成功した。

コンテナ起動時にホストで実行される`initializeCommand`で初回設定を登録する案も検討した。しかし、実機ログではホストの環境取得がCLI起動より先に行われ、使用バージョンのCLIではその後に`initializeCommand`を実行する。環境取得後に設定ファイルを変更しても、取得済みの値は更新されない。拡張がその後に再取得するかは未検証であり、初回の自動反映には依存しない。詳細と根拠は[検証記録](../development/wsl-ssh-agent-investigation.md)を参照する。

## Decision

WSLのagent利用に必要なログイン設定は、コンテナ接続前に利用者が実行する初回セットアップで登録する。共通処理はリポジトリで管理し、ホストの`~/.profile`から読み込む。設定登録の唯一の手段として`initializeCommand`を利用しない。

ログイン環境の準備ではagentの起動・再利用と接続先の設定を行う。パスフレーズ入力を伴う鍵の登録は、人が操作するWSLターミナルで行う。コンテナへの転送には引き続きDev Containersの標準機能を利用する。

## Consequences

- 初回にホスト側でセットアップを実行する必要がある。
- 設定を読み取る前に準備することで、同じ起動中の環境再取得に依存しない。
- agentの再起動で接続先が変わっても対応できる共通処理が必要になる。一時的なソケットパスの直書きは恒久設定にしない。
- 対話入力をログイン設定から分離し、VS Codeによる環境取得時の入力待ちを避ける。
