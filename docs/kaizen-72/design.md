# 会話ログの振り返りの設計

## 基本情報

- 対象Issue: #72
- 状態: 合意済み
- 合意日・合意対象: 2026-11-26、文書全体。未検証事項は試行し、成立しない場合は相談する。
- 正とする要求書: [requirements.md](requirements.md)

## 設計の概要

人間が最低限読む範囲は基本情報とこの節とする。後続の担当者は[詳細設計](#詳細設計)も読む。

### 全体構成

手動起動するSkillが、マージ済みPRと監査ログの対応を確かめ、利用者の選択に応じて対象を決める。セッションを小さな範囲に分け、子エージェントが流れを整理した後、親が全体の見取り図を作る。子が見取り図と隣接範囲の要点を参照して原文を再読し、親が結果を統合・原文照合してレポートを保存する。詳細は[対象の決定](#対象の決定req-001req-003)と[分析](#分析req-002req-004)を参照する。

### 主要な設計判断と採用理由

- [過去レポートを分析済みの正本とする](#対象の決定req-001req-003)。別台帳との不一致を避ける代わりに、レポート形式の検証と履歴の読み取りが必要になる。
- [機械的な分割と二段階の読み](#分析req-002req-004)で一度に扱う量を抑え、前後関係を補う。ただし二度読みの有効性とコストは未検証であり、試行して改善する。
- [中間結果を一時ファイルに置く](#分析req-002req-004)ことで会話への大量出力を避ける。ファイルのアクセス権と後始末が必要になる。

### 適用条件と運用上の制約

対象はリポジトリで管理される `docs/audit/` の監査ログであり、生ログは扱わない。GitHubのマージ済みPR情報を取得でき、ログとPRを一意に対応付けられる必要がある。ログ名の識別子とマージ済みPRのブランチ名を照合する。完全なブランチ名の復元は不要である。対応を確定できないログは理由を示し、利用者に分析へ含めるか確認する。取得失敗は完了扱いにしない。ログのマスクや欠落の修復は対象外である。

### 成立を確認した根拠と限界

既存実装は `timestamp`、`session_id`、`speaker`、`message` 等を持つJSONLを出力し、ブランチ名を安全なファイル名へ変換する。既存の復旧ログや同一セッションのブランチ間分割も存在する（[記録機構の検証](../testing/conversation-audit.md)）。2026-11-26に追跡済み監査ログと取得したマージ済みPR 23件を照合した。`docs-33-pr-writing` と `docs/33-pr-writing` は対応し、`docs-49` と `docs-49-audit` は共通の `docs-49` だけでは区別できないが、stem全体なら別々のPRに一致する。`env-28.recovered.jsonl` は復旧マニフェストで重複と確認でき、`env-44.jsonl` は取得したPRに一致せず、Issue #44の実装コミットはmainの第一親履歴にあるが、ログは後に別のPR #57で追加されている。ログの存在だけでは元ブランチのマージを証明できない。この確認は履歴全体の一意性を保証しない。子エージェントのファイル参照、分析品質、コンテキスト圧縮の観測はまだ試していない。成功を保証する設計ではなく、[検証方針](#検証方針)に従い確認する。

## 詳細設計

### 成果物・変更範囲

- `.agents/skills/` に手動分析用Skillを追加し、必要な場合に限り決定的処理のスクリプトを同じSkill内に置く。Skillの発見条件と実行手順を簡潔に記述する。
- `docs/` 配下に実行ごとのレポートを保存する。配置・機械可読形式は実装時に一意に定め、Skillと検証で共有する。
- 監査ログや記録機構は変更しない。重要な技術判断のADR要否は実装前に確認し、必要ならProposedとして記録する。

### 対象の決定（REQ-001、REQ-003）

1. GitHubのマージ済みPRをページ送りして取得し、ログのstem（拡張子を除く名前）と、PRのheadブランチ名の `/` を `-` に置換した値を照合する。`prefix-タスク番号` は候補の絞り込みに使い、後続の名前も含めて区別する。ログ名からブランチ名全体を復元しない。完全一致が1件の場合を候補とし、同名headの複数PR、衝突、対応なしは自動確定しない。理由と候補を提示し、ログごとに利用者へ分析に含めるか確認する。利用者による採用はマージを証明せず、手動採用として記録する。削除済みブランチやsquash mergeを祖先判定だけで除外しない。復旧用の重複ログは別途識別し二重分析しない。
2. 対応済み候補と未確定・失敗の件数と理由を示し、未確定ログの手動採用を確認してから、利用者に全件、未分析、個別選択を選ばせる。全件は対応済みと今回手動採用したログを含む。個別選択は分析済みも含む。採用されなかった未確定ログ、選択なし、候補なし、取得失敗を区別する。
3. 過去の完成レポートの機械可読な対象一覧から、リポジトリと監査ログの追跡パスの組を共通キーとして分析済みを判定する。PR番号は確定した場合のみ補助情報として記録する。手動採用時は採用理由、対応未確定、利用者の採用を記録し、架空のPR番号を付けない。同じログは後にPR対応が判明しても同一キーで扱う。パスの変更は自動追跡せず、別対象として通知する。再分析は新しいレポートを作る。対象外の後続変更を自動差分分析しない。形式不正のレポートを黙って無視せず通知し、未分析の正確性を確定できない場合は止める。
4. 対象確定時のログのパスと内容のハッシュを記録し、実行中に変化したら停止する。対象が途中で失敗した場合は完成対象に含めず、再試行可能な失敗として示す。

### 分析（REQ-002、REQ-004）

1. JSONLを行単位で検証し、ログパスとセッションIDの組を分析単位とする。同じセッションが複数ログに分かれた場合は別範囲とし、関係を示す。根拠はログパス、セッションID、行番号とし、実際の原文に戻れるようにする。
2. セッションを発言順に分割する。初期目安は範囲あたり最大100発言かつ本文合計40,000文字、境界の前後2発言を重複させる。閾値はトークン上限の保証ではなく試行で調整する。単一発言が上限を超えた場合は文字位置で分割し、行番号と文字範囲を保持する。重複は根拠単位で統合する。
3. 子が各範囲の流れと根拠位置を一時ファイルへ出力する。親はそれらを分割して読み、セッションの見取り図を作る。次に子が担当範囲の原文、見取り図、隣接要点を読み、良かった点・改善点と根拠を出力する。二度読みは仮説であり、代表シナリオの結果に応じて手順と閾値を改善する。
4. 親は中間結果を段階的に集約してセッション別・横断の傾向と一般的な次の行動を作る。結果も大量なら分割集約し、原文の根拠を個別に再確認する。推測と観測を区別し、根拠を確認できない発見を確定しない。子の出力・原文を会話に大量転記しない。
5. 一時ファイルはアクセスを制限した一時ディレクトリに作り、成功・失敗時に削除する。子の失敗、JSONL不正、読取・書込失敗、分割不能や容量超過は対象と理由を通知し、部分結果を完成扱いしない。完成レポートは一時ファイルから原子的に保存し、既存レポートを上書きしない。

レポートには実行日時、対象ログの共通キー・判定方法・手動採用理由・確定したPRとブランチ・ハッシュ、セッション別の内容・良かった点・改善点、横断傾向と次の行動、根拠位置、未分析・失敗と限界を記載する。対象一覧は完成分だけを機械可読にし、本文の根拠も追跡可能にする。

### 検証方針

- REQ-001・003: 隔離された小規模の履歴と模擬PR情報で全件・未分析・選択・再分析、squash、削除済みブランチ、名前衝突、復旧ログ、手動採用・不採用、後にPR対応が判明した同一ログ、ページ送り、取得失敗、不正な過去レポートを確認する。完成対象のみ分析済みとなること、複数回の保存で上書きしないことを確認する。
- REQ-002: 根拠が既知の合成会話を使い、各セッションと横断傾向、良かった点・改善点・行動、行番号と原文との一致を確認する。境界をまたぐ話題と重複も確認する。実ログの試行では本文を検証記録へ転記せず、品質と限界を記録する。
- REQ-004: 長い単一発言、大量セッション、大量の子結果、失敗と途中変更を試し、入力・結果の分割と失敗時の扱いを確認する。代表的大量ログで対象量、閾値、実行環境、親と子それぞれの圧縮有無を、実際に利用可能なランタイムの明示的な観測手段で記録する。観測手段・範囲を先に確認し、証拠がなければ不明と記録する。ログに圧縮イベントが記録されないことだけでは圧縮なしと判断しない。
- Skillの形式検証に加え、実際の手動起動と子エージェントへのファイル受け渡しを確認する。実環境で機能が使えない場合は代替を勝手に確定せず、制約と影響を報告する。

### 未決事項

上記の人間の判断に関わる事項に加え、実際に使用可能な圧縮の観測手段、実行時の分割閾値は未検証。ローカルのSkill・検証資料と `codex --help` では圧縮の有無を判定できる観測手段を確認できなかった。[Codex App Serverの公式資料](https://developers.openai.com/codex/app-server)は圧縮時の `contextCompaction` 項目を記載するが、この実行環境の親子セッションを同じ方法で観測できるか、通知の欠落がないかは未確認である。実装前の試行で確認し、方針の成立を妨げる場合は設計へ戻す。
