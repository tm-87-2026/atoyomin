# フロントエンドのアーキテクチャ

[全体構成と共通方針](../architecture.md)を前提とする。

## 画面の組み立て方

React公式の[Thinking in React](https://react.dev/learn/thinking-in-react)に沿って開発する。ReactでUIを組み立てるための設計手順として参照する。

1. ワイヤーフレームや画面案から、役割ごとにコンポーネントを分割する。
2. データを渡して表示する静的な画面を作る。
3. 変化を記憶するために必要な最小限のstateを特定する。
4. 各stateを利用するコンポーネントを確認し、stateを持つ場所を決める。
5. ユーザー操作からstateを更新し、表示へ反映する流れをつなぐ。

## state・propsとデータの流れ

stateは、コンポーネントが再描画をまたいで記憶し、更新を表示に反映する値である。propsは、親から子へ渡すデータや関数である。親のstateを子へ渡すと、その子にとってはpropsになる。

既存のstateやpropsから計算できる値は、原則として別のstateに保存しない。例えば一覧データと検索条件から絞り込み結果を計算できる場合、その結果を重複して保持しない。

stateを使うコンポーネントの共通の親など、適切な場所にstateを置く。データは親から子へpropsで渡す。子での操作が親のstateを変える場合は、親が渡した更新用の関数を子から呼ぶ。

APIから取得した結果は、コンポーネントのstateやデータ取得ライブラリで管理し、必要な子へpropsで渡す。取得中・失敗時の状態も表示に反映する。データ取得ライブラリの採否は未決定である。

## 責務の分離

上記の手順で実装し、表示・状態・操作の処理を追いにくくなった場合に、コンポーネントやカスタムHookへの分離を検討する。

カスタムHookはReactの状態を伴うロジックを分離・再利用する手段として扱う。通常の計算や判定まで一律にHookにしない。分離時は[React公式のカスタムHooksの指針](https://react.dev/learn/reusing-logic-with-custom-hooks)を参照する。

## コードの配置と依存関係

### 配置

原文は、コードの大部分を `src/features/` にまとめ、各機能のフォルダーにはその機能固有のコードを置くことを推奨している。アプリ全体で使うコードの配置例は次のとおり。

| 配置先 | 原文で示される用途 |
| --- | --- |
| `src/app/` | ルート・ページ、アプリの主コンポーネント、Provider、ルーター設定 |
| `src/assets/` | 画像やフォントなどの静的ファイル |
| `src/components/` | アプリ全体で共有するコンポーネント |
| `src/config/` | 全体の設定や環境変数の公開 |
| `src/features/` | 機能単位のモジュール |
| `src/hooks/` | アプリ全体で共有するHook |
| `src/lib/` | アプリ向けに初期設定した再利用可能なライブラリ |
| `src/stores/` | グローバルな状態ストア |
| `src/testing/` | テスト用ユーティリティーやモック |
| `src/types/` | 共有する型 |
| `src/utils/` | 共有するユーティリティー関数 |

各機能内の配置例は次のとおり。`<機能名>` は説明用の仮の表記である。

| 配置先 | 原文で示される用途 |
| --- | --- |
| `src/features/<機能名>/api/` | その機能のAPIリクエスト定義とAPI用Hook |
| `src/features/<機能名>/assets/` | その機能固有の静的ファイル |
| `src/features/<機能名>/components/` | その機能のコンポーネント |
| `src/features/<機能名>/hooks/` | その機能のHook |
| `src/features/<機能名>/stores/` | その機能の状態ストア |
| `src/features/<機能名>/types/` | その機能の型 |
| `src/features/<機能名>/utils/` | その機能のユーティリティー関数 |

原文では、各機能にすべてのフォルダーを作る必要はなく、必要なものだけを含めるとしている。また、機能間で共有するAPI呼び出しが多い場合には、機能の外の専用 `api/` にAPI呼び出しをまとめる選択肢も示している。

本プロジェクトでは、この配置を基本に必要なディレクトリーから作成する。具体的な機能名と境界は、実装時に決める。

### import

原文は次の方針を示している。

- 機能間の直接importを避け、アプリケーション層で機能を組み合わせることを勧めている。
- 共通部分を機能が利用し、機能と共通部分を `app/` が利用する、一方向の依存関係を推奨している。ESLintによる制約の例も示している。
- 機能の全ファイルをまとめて再エクスポートするbarrelファイルを介さず、必要なファイルを直接importすることを推奨している。理由としてViteの不要コード除去への影響を挙げている。

本プロジェクトでは、この推奨に基づき次のimportルールを採用する。表はフォルダー間の依存を示すもので、実行時のデータの流れを示すものではない。

| importする側 | importできる先 |
| --- | --- |
| `app/` | `app/` 内部、各機能、共通部分 |
| 各機能 | 同じ機能の内部、共通部分 |
| 共通部分 | 共通部分 |

機能間の直接import、および共通部分から機能・`app/` へのimportを行わない。複数機能の組み合わせは `app/` で行う。機能の全ファイルをまとめるbarrelファイルは作らず、必要なファイルを直接importする。

## 規約と自動検査

命名、相対パスを基本とするimport、型、書式は[コーディング規約](../conventions/coding.md)に従う。Bulletproof Reactの配置・依存方針の採用は、同リポジトリの規約やツール設定すべての採用を意味しない。

現在のESLint設定はJavaScript・TypeScriptの推奨ルール、React Hooks、React Refreshを対象とする。参照資料の `references/` は検査対象から除外する。機能間のimport制限・依存方向の自動検査は未導入であり、現時点ではレビューで確認する。自動検査を追加する際は、本書の依存ルールに合わせて設定する。
