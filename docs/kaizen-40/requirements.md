# Codexを前提とした開発ワークフローの要求

## 基本情報

- 対象Issue: #40
- 状態: 合意済み（2026-11-03）。設計・TODO洗い出しへ進むことをユーザーが承認した。

## 背景・目的

人間とCodexが開発を進める際の工程、成果物、役割、移行条件を定義する。工程名や順序だけでなく、各工程を新しいコンテキストから再開できることを目指す。

## 対象範囲

### 対象

Issueの作業用worktreeを開いた後の開発ワークフローと、その文書・Skillへの反映、代表的なタスクでの確認を扱う。すべてのタスクに共通する着手前の認識合わせと、実装タスク向けの4フェーズを定義する。

### 対象外

ブランチ・worktreeの準備は既存のタスク開始の責務とする。結合テストは将来の拡張とし、今回その具体的な運用までは定義しない。

## 要求

### REQ-001: ありたい姿のすり合わせ

- すべてのタスクで、作業前に目的・範囲・完了の目安をユーザーとCodexですり合わせる。
- 実装タスクの最初のフェーズでは手段に踏み込まず、実現したいこと、要求、対象範囲、完了条件をすり合わせる。

### REQ-002: 設計・TODO洗い出し

- 実装タスクの次のフェーズでは実現手段を具体化し、完了を追跡できる作業に分解する。

### REQ-003: TDDによる実装・単体テスト

- 実装系の作業はTDD（テスト駆動開発）で進める。
- 関連するケースを論理的なまとまりで用意し、意図した失敗を確認してから実装し、テストを通して必要な整理を行う。

- テスト1件ずつに固定せず、ひとつの振る舞いや関連する正常系・異常系などをまとめて扱う。
- 失敗原因と実装目的を追える範囲で、Codexがまとまりを判断する。

### REQ-004: 要求とTODOに基づく完了確認

- 実装タスクの最後のフェーズでは、新しいコンテキストで要求、TODO、実際の変更、検証結果を照合する。
- TODOの全件完了と要求の充足を確認する。

### REQ-005: 4フェーズのコンテキスト分離

- 実装タスクは原則として「ありたい姿のすり合わせ」「設計・TODO洗い出し」「実装・単体テスト」「完了確認」を、それぞれ別のコンテキストで進める。
- 設計とTODO洗い出しは同じコンテキスト、TDDのテスト作成と実装も同じコンテキストで扱う。

### REQ-006: 成果物による引き継ぎ

- 各工程のInput／Output、Outputに必ず含める内容、完了条件を明確にする。
- 次のフェーズには合意済みの成果物、必要な判断理由、未解決事項を渡す。
- 親や前担当の会話履歴、口頭の補足に依存せず再開できるよう、必要な合意と判断理由を成果物に記録する。
- 各工程では、指定された成果物に加え、適用規約・テンプレート・必要な既存コードや設定、現状資料を参照する。参照する成果物を直前の工程のものに限定しない。
- 検討途中の案と決定事項を区別し、会話全体を転記せずに再開できる形にする。

- 引き継ぎ時に不明点や矛盾が見つかった場合は、前の合意を確認する。

### REQ-007: Markdownを基本とする成果物

- 正式な成果物はMarkdownを基本とし、構造や流れの説明には適宜Mermaidを使う。
- HTMLは画面の動きや操作感を確認する補助資料として利用でき、そこで決まった仕様はMarkdownへ反映する。

### REQ-008: ブランチに対応する成果物の配置

- 配置先は `docs/<prefix>-<Issue番号>/` とする。
- prefixは既存のIssueラベルと作業ブランチの対応ルールに従い、作業ブランチに揃える。
- 今回の配置先は `docs/kaizen-40/` とする。

### REQ-009: フェーズごとの成果物

- 実装タスクのフェーズの成果物を次のファイルに記録する。
- 各ファイルは必要になったフェーズで作成する。

| ファイル | 内容 |
| --- | --- |
| `requirements.md` | ありたい姿、要求、対象範囲、完了条件 |
| `design.md` | 設計、判断理由、必要な図 |
| `todo.md` | 作業一覧、進捗 |
| `verification.md` | 完了確認の結果、残る課題 |

### REQ-010: 要求のトレーサビリティ

- 要求に安定したIDを付け、設計・TODO・完了確認から参照できるようにする。
- IDはIssue内で `REQ-001` 形式の連番とし、独立して充足を確認できる要求に付ける。背景や説明の一文ずつには付けない。
- 追加時は未使用の番号を使い、既存番号を振り直さない。削除した番号は再利用しない。
- 設計と各TODOには、対応する要求IDを記載する。
- 完了確認では、全要求の確認結果と、各TODOが対応する要求を確認する。
- 専用の対応表を別途必須にはせず、各成果物のID参照で追跡する。

### REQ-011: テンプレートによる見出しと要求表記の統一

- 要求書のテンプレートを用意し、大枠の見出し（レベル2）の名称と順序を固定する。
- その下には必要に応じて小見出しを追加できるようにする。

- 要求の表記は「レベル3の見出しに要求IDと要求名、その下に箇条書きの本文」に統一する。
- 各項目は確認しやすい単位で分け、箇条書きはネストせず同じ階層に揃える。
- 必要な説明用の表や図は対応する要求の下に置く。

### REQ-012: 仕様・設計の判断をADRへ記録

- 仕様や設計で重要な判断が必要になった場合は、適宜ADR（Architecture Decision Record、意思決定の記録）を作成する。
- 背景、検討した選択肢、決定内容、影響を残し、関連する成果物から参照できるようにする。
- 保存場所と形式、承認状態の扱いは既存のADR規約に従う。

### REQ-013: 要求・設計の合意によるフェーズ移行

- ありたい姿のすり合わせから設計・TODO洗い出しへ進む前に、ユーザーの明示的な合意を得る。
- 設計・TODO洗い出しから実装・単体テストへ進む前に、ユーザーの明示的な合意を得る。

### REQ-014: 完了確認の自律的な開始

- 実装・単体テストが終わった後は、ユーザーの確認を待たず、Codexが別コンテキストでの完了確認を開始してよい。

### REQ-015: 要求・設計変更時の相談

- 作業中に要求または設計の変更が必要になった場合は、どちらもユーザーに相談し、合意を得てから変更する。

### REQ-016: 小規模な変更の工程調整

- 小規模な変更では、ユーザーと合意した場合に工程をまとめられる。
- Codexの判断だけで工程や合意の区切りを省略しない。

### REQ-017: 非実装タスクの進め方

- 文書更新などの非実装タスクでも、作業前の認識合わせを行う。
- 認識合わせ後は、必要な作業と確認を行う。
- 非実装タスクに仕様書・設計書の作成や4フェーズを一律に求めず、別の専用フローも設けない。

### REQ-018: 完了結果の報告とコミット前の確認

- 完了確認を通過した後、Codexは変更内容・検証結果・残る課題をユーザーに報告する。
- コミット前にユーザーの確認を得る。完了確認の通過だけでは、コミット・push・PR作成へ自動的に進まない。
- コミットした場合は、既存規約に従って作業ブランチへpushする。
- コミット・push後、PR作成前に別途ユーザーの確認を得る。コミットの了承をPR作成の了承として扱わない。

## 完了条件

- 開発ワークフローをユーザーと合意している。
- 各段階の成果物、移行条件、役割、認識合わせのタイミングが明記されている。
- 合意した流れを適切な文書・Skillへ反映し、代表的なタスクで進め方を確認できる。
- REQ-001〜REQ-018の充足を確認できる。

## 未決事項

### 要求として未合意の事項

- なし。要求書全体についてユーザーの合意を得た。

### 設計フェーズで具体化する事項

以下は設計フェーズで案を具体化し、ユーザーに確認する。

- 各フェーズの具体的な完了・移行条件。合意が必要な区切りはREQ-013、完了確認の開始はREQ-014に従う。
- 要求・設計変更時の具体的な戻り方と、変更後のコンテキストの扱い。相談の要否はREQ-015に従う。
- コンテキストを切り替える操作と、次のコンテキストへ渡す開始情報。
- 既存のタスク開始・タスク起票・PR文面作成との責務の境界。
- 合意したワークフローを文書・Skillへ反映する構成と、代表的なタスクでの確認方法。
