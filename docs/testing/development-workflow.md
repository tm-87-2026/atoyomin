# 開発ワークフローの確認

## 目的と実施方法

成果物だけで工程を再開でき、合意や公開の境界で止まれるかを確認する。以下はIssue #40の実装に先立って定めた判定基準であり、実施結果ではない。対応要求は[要求書](../kaizen-40/requirements.md)、実施単位は[TODO](../kaizen-40/todo.md)を参照する。

一時ディレクトリに小さな機能追加のコードと成果物を用意し、完成した[Skill](../../.agents/skills/development-workflow/SKILL.md)を使う。各工程は会話履歴なしで新規起動し、開始指示・入力状態・成果物・観察結果を記録する。追加説明やユーザー介入が繰り返し必要なら、その負担も不足として残す。

合意前の停止を実際に観察し、その後は「検証専用の模擬合意」と明記した入力で進行を確かめる。模擬合意は本タスクの承認に流用しない。GitHubへの書き込み、コミット、push、PR作成は実行しない。例のコードは製品変更に含めない。

## 実施記録

### TODO-014：小さな機能追加（2026-11-08）

`/tmp/kaizen40-workflow-check/` に、文字列の前後空白を除去し小文字化する `normalize_label` の依頼を置いた。空文字列はValueError、文字列以外はTypeErrorとする3要求を用いた。例のコードは製品変更へ含めていない。一時パスは本セッションの検証場所であり、永続する参照先ではない。

次の表は、会話履歴を渡さず順番に起動した各サブエージェントの入力と、実際に観察した結果を示す。

| サブエージェント | 入力・操作 | 観察結果 |
| --- | --- | --- |
| check_requirements | Skill・正本・要求テンプレート・依頼を読む | REQ-001〜003の要求書を案として作成し、合意前に停止。設計・実装は行わなかった |
| check_design | 親が模擬合意を記録した要求書と規約・テンプレートを読む | 概要／詳細の設計書と要求ID付きTODOを作成し、設計・TODOの全体合意前に停止した |
| check_implementation | 模擬合意済み要求・設計・TODOを自分で読む | 同じサブエージェントが3つの振る舞いのTDDを反復し、失敗・成功の6ログを保存。3テストメソッド・11入力例成功。完了確認は行わず親へ返した |
| check_verification | 要求・設計・TODO・実コード・TDDログを読む | 全要求とTODOを照合し、テストを独立再実行して成功。verification.mdに通過と記録し、公開操作は行わなかった |

失敗の根拠は、変換3例の不一致、空判定3例のValueError未送出、不正な型5例のAttributeErrorまたはTypeError未送出。各段階の実装後に成功したことを `tdd-01〜03-red/green.log` と実施記録で確認した。完了確認の再実行も `python3 -m unittest -v` が終了コード0だった。

親は要求・設計の停止を確認した後、それぞれの成果物へ日付・対象と「検証専用の模擬合意」を記録した。後続には成果物のパスを渡し、前担当の観察記録・会話要約は入力にしなかった。ユーザーへの実際の追加確認は必要なく、親による模擬の状態更新だけで再開できた。全書き込みを一時fixtureに限定した。

## 検証の限界と残る課題

- 要求変更・設計変更後の追加の独立完了確認は実施していない。変更後のfixtureは確認待ちのままとし、正常ケースと実装漏れケースで検証した確認工程の成功を流用していない。
- 未決事項・工程調整・公開境界の一部は進行判断の検証であり、実際の全操作を実行したものではない。公開操作は確認基準どおり対象外とした。
- 実際のユーザーの応答時間、継続利用時の文書更新負担、履歴分離機能がない環境は未検証。実際のタスクで利用した際に不足として記録し見直す。
- ADR 0012は検証時点ではProposedだったが、2026-11-08にユーザーが本文を承認し、Acceptedへ更新した。
- Issue #40自体は、別のサブエージェントが全18要求・TODO-001〜022・実差分を照合し、[完了確認書](../kaizen-40/verification.md)で通過と判定した。文書構造14 Markdown、Skill形式、4fixtureの各3メソッド・11入力例を再実行して成功した。
