# 会話ログ記録機構の検証

## 目的

Codexとの会話が、監査ログとして正しく残ることを確認します。

次のファイルを変更した場合や、その変更をレビューする場合に実行してください。

- `.codex/hooks.json`
- `.codex/hooks/audit_transcript.py`
- `tools/codex_audit/`

## 検証の範囲

会話ログは、会話終了時にCodexから渡される記録をもとに作られます。自動テストでは、この記録を読み取り、監査ログを書き出すまでを確認します。アプリケーションの動作は対象外です。

| 検証レベル | 確認すること | 実行場所 | 監査ログへの影響 |
| --- | --- | --- | --- |
| 自動テスト | 会話の抽出、異常入力の検知、Stop Hookからのログ生成 | 一時的なGitリポジトリ | なし |
| 実環境確認 | Codexが設定済みのHookを実際に呼び出すこと | Codexの会話を終了したとき | 現在のブランチのログに追記 |

自動テストは実装の回帰を確認するものです。Hookの有効化やCodexランタイムとの接続まで確認する必要がある場合は、続けて実環境確認を行います。

## 自動テスト

### 前提条件

- Python 3
- Git
- リポジトリ直下でコマンドを実行すること（`.codex`、`docs`、`tests`、`tools` がある場所）

### 実行方法

```bash
python3 -m unittest discover -s tests/codex_audit -t . -v
```

環境変数の設定や、個別のテストファイルの指定は不要です。

### 成功の判断

実行したテストがすべて `ok` となり、最後に `OK` と表示されれば成功です。現在は次の3点を検証します。

| テスト | 保証すること |
| --- | --- |
| 可視メッセージの抽出 | ユーザーとCodexの会話だけを監査ログに含め、内部メッセージを除外すること |
| 異常入力の検知 | 会話イベントがない入力をエラーとして扱い、空のログを作らないこと |
| Stop Hookの連携 | Hook入力からブランチ別の監査ログJSONLを生成できること |

## 実環境確認

自動テストでは、隔離環境内のHookを検証します。実際のCodex環境での動作まで確認するには、Hookを有効化した状態で会話を終了し、次のファイルに今回の会話が追記されたことを確認します。

```text
docs/audit/<現在のブランチ名>.jsonl
```

このファイルが実運用の監査ログです。実環境確認はログを書き換えるため、必要な場合にだけ実施してください。

## 差分更新と障害確認

`event_msg` の会話イベントと `response_item` の user/assistant テキストに対応します。同じ発言が両形式にある場合は件数を対応させて二重出力を避けます。developer/system、analysisチャンネル、ツール出力、環境注入メッセージ、subagent由来の内部セッションは対象外です。

既存の公開ログはセッション別件数を追記位置として保持します。再実行時は未記録分だけを追加します。文面のマスクは維持されますが、公開ログの行削除、行の並べ替え、セッションIDの変更は行わないでください。今回のセッションは読み直しますが、既に取り込んだ過去セッションは再変換しません。未取り込みの過去セッションは個別に検証し、不正なものがあっても正常なものを反映します。

`.codex/audit-staging/<ブランチ名>.status.json` に、更新時点 `updated_at`、公開ログの総件数 `message_count`、セッション別件数 `session_counts`、最新発言時点 `latest_message_at`、失敗対象・元データの場所・理由 `errors` を保存します。ブランチ名の `/` は `-` に置き換えます。失敗がある場合、Hookは `systemMessage` で状態ファイルと理由を通知します。更新日時だけで完全と判断せず、`errors` が空であり、直前のユーザー発言と応答が公開ログ末尾付近にあり、件数・最新発言時点が原本と一致することを確認してください。状態ファイルの書き込み自体が失敗した場合はHookの通知を確認します。

テストでは二形式の単独・併存、同文の繰り返し、複数セッション、マスク保持、再実行、不正な過去記録がある場合の部分反映とHook通知、原本の書き換え検知を確認します。

## 原本からの復旧

1. 公開ログと `.codex/audit-staging/` を非公開の場所へバックアップします。状態ファイルの失敗対象を確認します。
2. Codexが保持する元セッション（通常は `$CODEX_HOME/sessions/` または `~/.codex/sessions/` 配下）をセッションIDで特定します。ステージ済みコピーより元データの更新日時・行数・最終イベント時点が新しいか確認します。失敗した元データは削除せず保持します。
3. 既存のコピーを残したまま、新しい元データを指定してHookを再実行します。リポジトリ直下で、対象ブランチをチェックアウトして実行します。

   ```bash
   python3 .codex/hooks/audit_transcript.py <<'JSON'
   {"cwd":"/absolute/path/to/repository","session_id":"original-session-id","transcript_path":"/absolute/path/to/newer-session.jsonl"}
   JSON
   ```

4. 先頭の内容が変更されている場合や、新しい形式の抽出件数と既存ログの対応が不明な場合は、自動更新を進めず、別ファイルへ抽出してセッションごとの文面と順序を照合します。既存ログに既に欠落がある場合も同様です。公開ログを全再生成するとマスクが失われるため、個別に不足分を照合して復元します。
5. 状態ファイルと公開ログのセッション別件数・最新発言時点を確認します。再実行して件数が増えないことも確認します。今回のenv/28復元成果物の再生成はこの機構修正とは別に扱います。

## 公開ログと原本の扱い

生セッションとステージ済みコピー、状態ファイルはローカルの非公開資料です。Gitへ追加しません。自動マスク機能はありません。公開する `docs/audit/` の差分は、個人情報・認証情報・内部パスなどを確認して必要な箇所をマスクします。公開ログのマスクは原本へ反映されないため、原本のアクセス権限と保持期間は別に管理します。障害報告には会話本文を貼らず、失敗対象と形式エラーだけを共有します。
