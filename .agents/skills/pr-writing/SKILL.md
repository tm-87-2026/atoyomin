# PRの文章作成・レビュー

## 目的

会話を読んでいないレビュアーが、問題・変更後の動作・検証結果を短く把握できる文章を作る。

## 入力

Skillを使うエージェントは、依頼と作業コンテキストから対象を特定し、文面の根拠を収集する。利用者にすべての資料の提出を求めない。

| 区分 | 情報・扱い |
| --- | --- |
| 依頼から特定する情報 | 対象リポジトリ・Issue・PR、作成／修正／レビューの別、文面の承認に関する指定 |
| エージェントが収集する根拠 | 対象Issueの要求・完了条件、最終的な差分・関連文書、検証記録、既存PR・テンプレート。依頼に必要なものを確認する |
| 不足時の扱い | 作業コンテキストやツールから取得できる情報は取得する。判断に必要な情報がなお不足する場合だけ質問し、確認できない事実を推測で補わない |

GitHubから取得するときは、[APIの参照先](references/github-api.md)を読む。既存PRの文面だけで変更内容を判断しない。

## 手順

1. 「入力」に従って対象と依頼の種類を特定し、根拠を収集する。PRのbaseとheadの差分で、追加・変更・削除のどれかを判断する。作業途中のコミットや会話中の案を変更前の状態にしない。問題・変更後の動作・必要な設計上の判断・検証結果を整理する。
2. 依頼に応じて、次の成果物を作る。

   | 依頼 | 成果物 |
   | --- | --- |
   | 作成・修正 | 最終的な変更に合うタイトルと本文 |
   | レビュー | 問題のある箇所と理由、改善案。問題がなければその旨 |

3. 「文章の基準」と「確認項目」に照らして推敲する。
4. ローカルの案を提示する。外部への反映は「承認・反映」に従う。

## 文章の基準

### タイトル

- 対象と何が変わるかを具体的に示す。「対応する」「改善する」だけで済ませない。
- 接頭辞などはリポジトリの慣例に合わせる。

### 本文

| 見出し | 役割 |
| --- | --- |
| 背景 | なぜこのPRが必要か。解決したい問題や実現したい機能を伝える |
| 変更内容 | 今回何を変更し、何ができる・どう動くようになったかを伝える。実現手段はなるべく混ぜない |
| 設計上の判断（任意） | 何を、なぜ選んだか。判断に必要な選択肢と、受け入れた制約・代償を伝える |
| 検証 | 意図した動作や懸念した問題を、どう確かめ、何が分かったかを伝える。重要な未確認事項も示す |

- 基本は「背景」「変更内容」「検証」の順に書く。レビューしてほしい選択やトレードオフがある場合だけ、「変更内容」と「検証」の間に「設計上の判断」を追加する。該当する判断がなければ見出しごと省く。
- リポジトリのテンプレートがある場合は、その見出しに役割を対応させる。
- 「設計上の判断」では、選択理由を理解するために必要な実現方法を説明する。重要な判断をADRに残す場合は、PRには要点とリンクを書く。
- 各節は短くまとめる。並列する変更は箇条書きにし、検証は下記の表で示す。
- 読み手の前提はbaseブランチの状態とする。baseに存在しない成果物は「追加」と書き、途中案への指摘・修正を「分離」「変更」などの目的として説明しない。
- 別タスクの予定や今回扱わない範囲は、必要なら末尾の「補足」に置く。「変更内容」には今回の差分による成果だけを書く。
- 「変更内容」の同じ階層には、同じ粒度の変更を並べる。追加する成果物と、その中の方針・資料を同列にしない。1つの成果物に含まれる内容は、導入文と箇条書き、または親子の箇条書きで示す。
- スコープが変わった場合は、最終的な変更に合わせてタイトルと本文を書き直す。

### 情報量・根拠

| 情報 | 扱い |
| --- | --- |
| 共通認識の目的・一般論 | 繰り返さない |
| 理解に必要な用語 | 初出で短く補足する。補足が増えるなら平易な言葉に置き換える |
| 実現方法 | 「設計上の判断」で選択理由・効果・制約の理解に必要な範囲を書く。検証方法は「検証」に書く |
| 内部の識別子・ファイル名・処理順 | 動作の説明の代わりに列挙しない。詳しい設計・手順は関連文書へリンクする |
| 会話の経緯・試行錯誤・利用者からの指摘 | 本文に入れない |
| 検証結果 | 確認した記録に基づく。過去の結果を今回実行した結果として扱わない |

### 検証の書き方

検証済みの内容を「検証項目」「方法」の2列の表で書く。結果列は設けない。複数のSkillや機能を検証する場合は、対象ごとに小見出しと表を分ける。対象を示すためだけに列を追加して表の横幅を圧迫しない。共通の検証は別の表にまとめる。項目は確認済みの動作・性質、方法は実施したコマンド・操作・確認対象を示す。失敗や未確認事項は検証済みの表に混ぜず、表の外に記載する。複数の検証を一段落に詰めず、自動検証と利用者による実画面の確認を区別する。

| 検証項目 | 方法 |
| --- | --- |
| 追加成果物の形式 | 対象の検証コマンドを実行 |

### 未検証事項

- 未検証の項目には、検証していない理由と今後の扱いを書く。後で検証するのか、実際に使って問題があれば修正するのかなど、今回どのように扱う判断をしたかを伝える。
- 理由・方針は利用者の発言や関連文書、過去の会話ログから確認する。分からない場合は利用者に質問し、推測で補わない。

### レビューコメント

次の順で、修正の判断に必要な内容を伝える。

1. **対象**: どの箇所についてのコメントか。
2. **問題と影響**: 何が問題で、読者や動作にどう影響するか。
3. **提案・質問**: 修正案、または確認したい点。

文面のレビューでは、読み取りにくい理由と短い改善案を示す。技術的な不具合と表現上の提案を区別し、好みを不具合として扱わない。問題がなければ指摘を作らない。

## 確認項目

- [ ] 冒頭で、何が問題でどう変わるか分かる。
- [ ] baseとの差分で追加・変更を判断し、作業途中の案や指摘を変更前の状態としていない。
- [ ] 別タスクの予定は変更内容に混ぜず、必要なら補足に置いている。
- [ ] 検証済み項目は項目・方法の2列の表になり、実行記録と対応している。
- [ ] 必要な用語の補足があり、共通認識や実装詳細を説明しすぎていない。
- [ ] 変更内容と検証結果が根拠に一致し、未確認のことを確認済みにしていない。
- [ ] 各見出しが役割を果たし、「変更内容」に実現手段が混ざりすぎていない。
- [ ] レビューに必要な選択理由・制約を「設計上の判断」で説明している。該当しない場合は省いている。
- [ ] 変更内容の同じ階層に、成果物とその内訳が混ざっていない。
- [ ] 本文は変更全体を説明し、レビューコメントは対象箇所への指摘になっている。

## 承認・反映

| 状態 | 行動 |
| --- | --- |
| 利用者が文面の承認を求めている | ローカルの案と確認結果を提示して待つ。承認前に、その文面を含むコミット・プッシュ、PR作成・更新、コメント投稿を行わない |
| レビューだけを依頼されている | 指摘と改善案を提示する。依頼だけで本文更新やコメント投稿も許可されたと判断しない |
| 承認待ちがなく、反映も許可されている | 既存の作業許可とリポジトリ規約に従う。このSkillだけを理由に確認を増やさない |
