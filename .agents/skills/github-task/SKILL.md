# GitHubタスク操作

## 対象と操作経路

- 依頼のURL、または `git remote get-url origin` から対象の `owner/name` を特定する。番号だけで他のリポジトリを検索しない。
- リポジトリの `AGENTS.md` と変更対象に適用される規約を確認する。
- API操作の前に[認証・接続手順](../../../docs/development/github-api.md)を読み、コマンドは[操作例](../../../docs/development/github-api-operations.md)を参照する。Issue・PR・Projectsはリポジトリ直下で `bash tools/gh.sh` を使う。Gitの取得・pushは既存のSSH接続を使う。
- PATの読み込みはラッパーに任せ、認証情報を表示・記録しない。CLIの引数やJSON項目は必要に応じて対象コマンドの `--help` で確認する。

## タスクを参照する

`issue view <番号> --repo <owner/name> --comments` で本文・会話を読み、必要に応じてJSONで担当者・ラベル・Project登録を取得する。関連Issue・PRは本文・コメント・リンクからたどり、要求と完了条件、現在の進捗を確認する。標準出力で取得できない履歴・関連情報はラッパーの `api` で補う。

ProjectはIssueの登録先や依頼から特定する。候補が複数あって判断できなければ確認する。項目の照合にはタイトルだけでなくIssueのURLまたはリポジトリと番号を使う。項目やフィールドの一覧はページ数・取得上限を確認し、対象が見つかる前に「未登録」と決めない。

## 新しいタスクを切る

1. 同じ目的のIssueを開閉両方の状態で検索し、候補の本文を確認する。起票者が同じという理由だけで同一タスクにしない。
2. 同じ目的の未完了Issueがあれば、その要求を保持して不足を更新する。完了済みなら今回の追加要件を切り分け、関連を記載した新規Issueにする。
3. タイトルは対象と行う変更を具体的に示し、本文には目的・背景、対応内容、確認可能な完了条件、必要な関連リンクを書く。長い本文は一時ファイルに書いて `--body-file` で渡す。
4. 既存ラベルの説明を確認し、タスクの主目的に合う**1個**を付ける。合うものがなければ新設を即断せず相談する。既存Issueのラベルを直すときは変更対象と現在値を確認する。
5. 担当者は明示された人を設定する。本人の作業依頼なら `api user` などで本人のアカウントを確認する。過去タスクへの設定は関連PR・作業記録から担当実績を確認し、起票者だけから推定しない。既存担当者を無断で外さない。担当未定の起票で自動的に自分へ割り当てない。
6. 対象Projectを確認して登録する。既存登録を重複させず、未着手のStatusはProjectの選択肢に合わせる。

## 「#番号に着手する」

- 要求・完了条件と関連資料を読み、現在のブランチ・未コミット変更・既存PRを確認する。既に専用ブランチがあれば再利用し、別タスクの作業や利用者の変更を上書きしない。
- 新規なら既存の命名に合わせて専用ブランチを作る（例: 環境整備なら `env/<Issue番号>`）。分岐元が適切か確認し、無関係な変更を混ぜない。
- 担当者とProject登録を確認する。本人の着手依頼なら本人を担当に追加し、実際に作業を開始した段階でStatusを進行中にする。Project・フィールド・選択肢のIDは一覧から取得し、別タスクのIDを流用しない。
- 実装・必要な文書更新・変更に応じた検証を進める。完了条件を満たす単位でコミットし、pushはリポジトリ規約に従う。

## 進捗更新・PR作成・完了

- 進捗は実際の作業と検証結果に基づいて更新する。部分完了なら残作業や阻害要因を区別する。
- PR作成依頼、または作業の許可範囲にPR作成が含まれる場合は、既存PRの有無、差分、検証、push先を確認する。タイトル・本文は[pr-writing](../pr-writing/SKILL.md)に従い、対象Issueを関連付ける。文面の承認待ちがあれば公開前に待つ。
- コード変更ではPR作成やpushだけでIssueを閉じたりProjectをDoneにしない。マージと完了条件を確認する。PRを必要としないタスクも成果と完了条件で判断する。
- 完了の反映が許可されている場合にIssueの状態とProjectのStatusを更新し、自動連携があれば先に反映済みか確認する。

## 実行条件と確認

タスクの起票・着手・進捗更新の依頼は、その範囲で必要なIssue・Project・担当者・ラベルの更新を含む。参照や相談だけの依頼を更新許可に読み替えない。既存の許可を毎回聞き直さず、マージ・削除など依頼外の操作を追加しない。

書き込み後は対象を再取得し、Issueの本文・ラベル・担当者、Project項目のStatusなど変更した値を確認する。最終報告には対象リンク、変更結果、残作業を示す。

通信失敗などで成否が不明なら、再取得してから再実行を判断する。IssueやProject項目の作成を確認せず繰り返さない。認証・権限不足なら対象・組織・必要権限を接続手順に照らして確認し、同じ失敗を反復したり権限を一律に広げたりしない。取得できない情報と未反映の操作を報告し、ローカルで進められる作業を続ける。
