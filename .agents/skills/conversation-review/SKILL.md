# 会話ログの振り返り

対象はGitで追跡中の `docs/audit/*.jsonl` だけとし、生ログ、未追跡ファイル、記録機構の変更は扱わない。リポジトリの [GitHub API操作手順](../../../docs/development/github-api.md) を確認する。GitHubから取得できない場合は分析済みとせず、理由を伝えて停止する。

## 対象を決める

1. ページ送りでマージ済みPRをすべて取得し、headブランチ名の `/` を `-` に置き換えた値とログのstem全体を照合する。完全一致が1件のみなら対応済みとする。同名headの複数PR、変換後の衝突、対応なしは確定せず、ログごとに理由と候補を提示し、利用者に採用の可否を尋ねる。手動採用はマージの証明ではない。復旧マニフェスト等を調べて重複と確認できた復旧ログは二重に分析しない。祖先判定だけでsquash mergeや削除済みブランチを除外しない。
2. `docs/conversation-reviews/*.md` の完成レポートを読み、次の機械可読ブロックの `repository` と `path` の組を分析済みキーとする。同一レポート内の形式不正、必須項目の欠落、重複キーなどで未分析の正確性を確認できないときは通知して停止する。別のレポート間では再分析により同じキーが現れ得るため、分析済みキーとして統合する。パス変更は別キーとして通知する。
3. 対応済みと未確定の件数・理由を示し、手動採用を確認してから全件、未分析、個別選択を尋ねる。全件は対応済みと今回手動採用したものを含む。個別選択では分析済みも選べる。候補なし、選択なし、不採用、取得失敗を区別して通知する。再分析では新しいレポートを作る。
4. 対象ごとに追跡パスとSHA-256を記録し、作業中と保存直前に再確認する。変化した対象や処理が失敗した対象は完成対象に含めず、理由と再試行可能な状態を報告する。

## 分析する

権限を制限した一時ディレクトリを作り、中間ファイルをそこに保存する。成功・失敗を問わず最後に削除する。JSONLを行ごとに検証し、ログパスとsession_idの組を分析単位とする。同じセッションが複数ログに分かれている場合は別範囲とし、その関係を示す。

対象確定後、リポジトリルートで `python3 .agents/skills/conversation-review/scripts/extract_signals.py <対象JSONL>... > <一時ディレクトリ内の出力JSON>` を実行する。出力する訂正・介入、確認質問、完全一致反復は表層候補であり、採否や良否ではない。候補の前後を読み、採用・不採用・判定不能を後段の文脈判断として分けて記録する。値の大小や閾値への一致だけを、継続・改善の根拠にしない。

人間の指示、判断、提案した進め方を評価するときは、[人間とコーディングエージェントの協働を評価する観点](references/human-collaboration-practices.md)を読む。Codexの応答は人間の発言の前後文脈としてだけ参照し、評価対象にしない。外部資料の明記、ログ評価への推論、適用範囲、不明条件を区別し、観点の有無だけで採点しない。

発言順に最大100発言かつ本文40,000文字を目安として範囲を作り、境界の前後2発言を重複させる。単一発言が40,000文字を超えたら文字位置で分割し、行番号と文字範囲を保つ。重複する根拠は統合する。分割不能、容量超過、JSONL不正、読書き・子の失敗は対象と理由を示し、部分結果を完成扱いしない。

各範囲を子エージェントに渡し、まず流れ、人間の行動、根拠位置を一時ファイルへ書かせる。親は中間結果を分割して読み、セッションの見取り図を作る。次に子は担当範囲の原文、見取り図、隣接範囲の要点、シグナルが示した候補位置を再読し、所見候補と根拠を別の一時ファイルへ書く。この二段階を省略しない。子への指示はファイルパスと担当範囲に絞る。子は担当範囲や隣接箇所を必要に応じてツール出力で読み、親も根拠照合に必要な範囲を読む。最終報告などへの原文や結果の不要な大量転載は避ける。子を利用できない場合は代替方法を勝手に確定せず、利用者に制約と影響を伝える。

親は結果を段階的に集約する。結果が大量なら分割集約し、各発見のログパス・session_id・行番号と必要な文字範囲を原文と照合する。同じ人間の行動を示す所見候補は、単一ログ内でも複数ログ間でも統合し、すべての対象ログと根拠位置を残す。境界の重複部分から得た候補は二重計上せず、同じ根拠として統合する。

所見を確定するときは、次を守る。

- 評価対象は人間の指示、判断、提案した進め方だけとする。Codexの応答は、人間が何へ反応したかを理解する前後文脈に限って参照する。
- 観察事実、そこからの解釈、次回への提案を分ける。人間の意図、成果、原因をログから確認できない場合は推測で埋めず「不明」とする。
- 各所見を単一セッションの出来事か、複数セッション・複数ログを横断する傾向かに分類する。根拠ごとに対象ログ、`session_id`、行番号、必要な文字範囲、人間発言の必要最小限の引用を付ける。
- 改善すべき点は、十分なログ根拠があり、適用可能な公式プラクティスとの関係を説明できる場合だけ確定する。根拠が弱い候補は改善点へ入れず、不明・限界へ記録する。
- 改善すべき点には関連する `PRACTICE-ID` と出典URLを付ける。資料に明記された内容、ログ評価へ当てはめる推論、製品・機能・タスク種別の適用条件、ログだけでは確認できない不明条件を分ける。資料同士が異なる場合や製品固有の推奨を一般化できない場合は断定しない。
- シグナルは再読する位置を決める入口として使う。シグナルに現れない所見も範囲読解から拾い、シグナル値だけで人間の行動の良否を決めない。

コンテキスト圧縮を検知できる実行環境では、親と子それぞれについて観測方法、対象、結果を記録する。検知手段がない場合やイベントを観測できない場合は「圧縮なし」とせず「不明」とする。子の失敗、JSONL不正、読書き失敗、分割不能、容量超過、対象ハッシュの変化のいずれかがあれば、成功した範囲だけで完成レポートを作らず、対象と原因を失敗として報告する。

## 保存する

完成レポートは [レポートテンプレート](references/report-template.md) に従う。`継続すべき点` と `改善すべき点` を主構造とし、ブランチ別・セッション別の見出しを主構造にしない。実行情報と対象、機械データ、継続すべき点、改善すべき点、次回に試す行動、不明・未分析・失敗・限界の順に置く。

機械データには対象期間と対象ログを明記する。冒頭でラリー、修正・介入、確認質問、反復、長大化について「何を数えるか」と「値から何を探せるか」を初見の読者向けに簡潔に説明する。

機械データの主表示は、1行をブランチまたはログとするMarkdown表のダッシュボードにする。各行にはセッション数・人間ターン数・Codexターン数、ラリー数と1セッション当たりの値、訂正・介入と確認質問の機械候補数・文脈上の採用数・率と分母、反復の採用数・率と分母、長大化の該当数・全セッション数・最長セッションの発言数と文字数、読むログ・`session_id`・行番号または範囲とそこで探せることを示す。ターンは連続する同一話者の発言まとまりとし、訂正・介入と反復は人間ターン、確認質問はCodexターンを率の分母にする。LLMによる採否は機械候補数と分け、取得不能・判定不能をゼロとして扱わない。全体合計はダッシュボードの後の補助情報にする。少数データや値だけで対象の優劣を断定しない。

ログ別ラリー数の横棒グラフを必ず置く。Mermaid互換性を仮定せず、通常のMarkdownで表示できる等幅コードブロックを使い、各棒の末尾にダッシュボードと同じ正確な値を付ける。棒を縮尺表示しても値を丸めない。率や長大化を可視化する場合は、比較に価値があるときだけ追加し、件数と異なる軸へ分ける。この欄はドリルダウンの入口であり、所見の結論や「読む理由と限界」のような分析者向け心得を主表へ置かない。抽出・判断上の限界は「不明・未分析・失敗・限界」へ短くまとめる。

`継続すべき点` と `改善すべき点` のタイトル、解釈、提案は、複数タスクで再利用できる人間のCodex活用行動として書く。個別タスク固有の出来事は観察事実と根拠例に置く。`次回に試す行動` は、人間がCodexへ与える指示、人間が事前に行う判断、人間が逸脱時に行う介入、人間が続ける習慣だけにする。Codex自身の分析・実装手順や、Codex利用に固有でない一般的な開発作業は行動にしない。

`docs/conversation-reviews/` に実行ごとのMarkdownを一時ファイルから原子的に保存し、既存ファイルを上書きしない。再分析では旧レポートを残し、新しいファイルへ保存して比較対象の旧レポートを記す。完成対象だけを以下のJSONブロックに記録する。`repository` は `owner/repo`、`path` はリポジトリ相対の追跡パスとし、`sha256` は対象確定時のハッシュとする。確定した場合だけ `pr` と `branch` を含める。手動採用では `method` を `manual` とし、`reason` に対応未確定の理由と利用者が採用した事実を記載する。自動照合では `method` を `matched` とする。

```json conversation-review-targets
{"version":1,"targets":[{"repository":"owner/repo","path":"docs/audit/example.jsonl","sha256":"<sha256>","method":"matched","pr":1,"branch":"example"}]}
```

保存前に、各所見の引用と位置を原文へ照合し、観察事実・解釈・提案が混在していないこと、改善点の公式資料の明記・ログへの推論・適用条件・不明条件が分かれていることを確認する。手動採用の理由と利用者による採用も記録する。
